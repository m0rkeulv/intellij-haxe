# Generated-code preview from compiler blueprints

Feasibility research and design record: rendering the compiler's post-macro
view as a read-only "virtual source" file, so navigating to a macro-generated
member lands in a readable reconstruction of the type.

Status: the dump-based navigation path is BUILT and sandbox-verified against
a haxeui project (grammar `unboundIdentifier`, `HaxeGeneratedDumpService`,
`HaxeGeneratedCodePreview`, goto handler, per-file highlighting level +
semantic-annotator guards); the blueprint-render enrichment
(docs/meta/initializers in the synthetic extern) remains future work.

## What the compiler offers

`server/type` (and `server/module` for a whole module at once) serializes the
post-macro type with the generator's **full config** (`create_full_config` in
`src/context/display/displayJson.ml` → `genjson.ml`): docs, positions and
expression data are all enabled. Per class field (`JsonClassField` in std
`haxe/display/JsonModuleTypes.hx`) the payload carries:

| Available | Field |
|---|---|
| name + fully resolved type | `name`, `type` (JsonType) |
| visibility / modifiers | `isPublic`, `isFinal`, `isAbstract`, `scope` (Static / Member / Constructor) |
| kind incl. property access | `kind` (FVar / FProp with read/write access, FMethod) |
| type parameters | `params` |
| metadata | `meta` |
| doc comment | `doc` |
| position | `pos` (file + range) |
| overloads | `overloads` |
| initializer (vars only) | `expr` — printed from the field's `@:value` metadata when present |

Class-level: `superClass`, `interfaces`, `isInterface`, `isExtern`,
`constructor`, `init`, `overrides`. Enums, typedefs and abstracts have their
own equally complete shapes (abstracts include from/to casts and operators).

**The hard limit: method bodies are never in the JSON.** `genjson.ml` emits
`expr: null` for every method regardless of config — the protocol was built
for signatures, not code. Any preview built on the display server is
decompiler-stub style: full declarations, no bodies.

Known constraints from the display-protocol README (live-verified):
`server/*` introspection needs an actual compile through the server first,
and `Context.defineType` modules are invisible to `server/modules` — they are
found via the dependency sweep and answered by `server/type` on their dot
path.

## What the plugin already has

`HaxeCompilerResolveService.buildBlueprintFile` already renders a virtual
`extern class` from the blueprint as real non-physical PSI, and resolve
navigation already lands in it. The user-visible half of the idea exists;
what is missing is richness. The current render keeps only name + type:

- everything is hardcoded `public`; `isPublic`/`isFinal` are dropped
- property access is lost (`FProp` renders as a plain `var`)
- doc comments, metadata, `@:value` initializers, overloads: dropped
- no `extends`/`implements` clause, no constructor marking
- `TypeBlueprint` (the DTO) only parses `name`, `kind`, `fields`, `statics`

So "reconstruct the result as a virtual file" is an enrichment of an existing
mechanism, not a new subsystem.

## Path to a real preview

1. **Widen `TypeBlueprint`** to carry doc, meta, pos, visibility, property
   read/write, `@:value` expr, and class-level extends/implements/kind.
   (Cache size impact is small; blueprints are per-type and already cached.)
2. **Render a full stub file**: doc comments, metadata lines,
   `var (get, set)` property syntax, `= initializer` where `@:value` exists,
   `extends`/`implements`, constructor. Members whose `pos` points into a
   real project source file are the non-generated ones — the generated
   members are exactly those with no matching source declaration, and can be
   marked (e.g. a `/** generated */` line or a separate section).
3. **Present it read-only**: the render already lives in a non-physical
   `HaxeFile`; giving it a stable name (`TypeName (compiler blueprint)`) and
   an editor notification banner ("Post-macro blueprint — generated by the
   compiler, read only") makes it a first-class preview, same UX pattern as
   the platform's decompiled-class viewer.
4. **Optional**: `server/module` renders the whole module in one file, which
   matches Haxe's module semantics (several types per file).

Needs live verification before building (pin in `LiveDisplayServerTest`):
whether `@:value` metadata (and thus initializer text) is present for
ordinary field initializers or only for constants, and the exact `pos`
shape/behaviour for generated members (macro position? build-macro input?).

## Navigation wiring (design decision)

The feature exists only when the compilation server is running and the
compiler-resolve path is available — the same gates
`HaxeCompilerResolveService` already enforces (compiler completion mode +
per-container compilation-server opt-in). No new setting.

Go-to-declaration on a member that resolves ONLY through compiler logic
(a blueprint-resolved member with no source declaration) opens the preview
file and places the caret on the matching named member. The preview is real
Haxe PSI, so the landing point is found by name through the class model
(class by dot path, member by name, caret at the member's name identifier)
— the same lookup `blueprintMember` does today against the slim extern
render; the upgrade is the richer file plus a real editor tab
(`OpenFileDescriptor` at the member's offset) instead of a bare synthetic
declaration.

The dump variant slots into the same flow: the build context that the
display service already derives (active build file → target) determines
`dump/<target>/`, so the module's dump file is addressable without asking
the user anything.

## Debugging and the preview

Breakpoints cannot target the preview: it is a LightVirtualFile with no
stable URL (the gutter refuses before debugging starts), and no runtime
debug info — source maps, HashLink bytecode info, hxcpp — references the
preview; locations there are real file path + line. Line arithmetic against
the preview (banner offset etc.) is irrelevant: the dump's layout is
unrelated to compiled positions.

What works today: macro-generated code carries POSITIONS OF REAL FILES (the
dump's trace infos show it: a generated handler embeds
`fileName : "src/MainView.hx"`), so stepping into a generated method
stops fine and opens the real file at the macro-assigned position, and a
breakpoint on a real-source line whose position generated code borrowed is
hit by that generated code.

Measured on the haxeui hello world's js source map: generated code IS
mapped, onto the real-file lines the macro assigned — the whole XML-built
constructor body maps to the constructor declaration line (29 segments on
one line), the bind-wiring to the `@:bind` metadata line. Stepping
into it therefore works but displays a frozen caret on that one line; the
IDE's Smart Step Into even lists the generated builder as a target labeled
with the `@:build(...)` source text (it names targets by their mapped
original range).

Verified on a HashLink build (decompiled bytecode): the generated
constructor is statement-for-statement the dump's constructor — the preview
shows exactly what runs. The debugger there stopped with the frame
"MainView.new (ComponentMacros.hx:317)": generated expressions carry the
position the macro gave them, and haxeui builds its expressions by
reification, whose default position is the reification site inside the
MACRO's own source. Stepping into a generated constructor can therefore
land in macro-library code that is not executing — positions are a
patchwork of the user's file (explicitly positioned parts like the
`@:bind` wiring) and the macro implementation (reified parts).

hxcpp adds a third flavor: its generated C++ stamps stack frames with the
DECLARING class's file but per-statement LINES from the typed-AST position
— the same generated statement that HL reported as "ComponentMacros.hx:317"
appears as "MainView.hx:317", a line number past the end of a 19-line file.
File and line come from different sources and need not agree.

Future option: show the PREVIEW as the stopped-frame view when the debugger
stops in generated code. Detector needs BOTH signals: (a) the frame's
METHOD belongs to a class whose declaring file is not the frame's FILE
("MainView.new" reported in ComponentMacros.hx — HL/js), and (b) the
frame's line does not exist in the frame's file (MainView.hx:317 in a
19-line file — hxcpp's mixed encoding). Read-only display, so none of the
breakpoint blockers apply; statement order in the preview matches the
generator's input, so statement-level sync is feasible.

## Method bodies — out of reach, with one escape hatch

If body-level reconstruction is ever wanted, the only compiler feature that
emits post-macro bodies is `-D dump=pretty`: a normal compile then writes the
typed AST of every module under `dump/<target>/...`, readable but not valid
Haxe. There is no per-type filter — every module in the compilation is
dumped, std included. Measured on haxe 4.3.7 (hello-world, js): ~95 ms
compile grows to ~118 ms with `dump=pretty`, i.e. ~0.4 ms per dumped module
(58 files). Extrapolated, even a thousand-module project pays well under a
second of dump overhead on top of its (server-cached) build, and because
everything dumps at once, the first navigation pays for all later ones —
cache the dump dir keyed by build signature and invalidate on the next
build. Re-measure on a real lime/openfl project before relying on this. That could back an explicit opt-in action ("Dump typed AST for this
build") that opens the module's dump file — a separate whole-compile with
file output, so it must never run implicitly. Injecting `--macro` hooks into
the user's build to print `TypeDefinition`s was considered and rejected:
invasive, lossy (typed AST ≠ macro AST), and it changes the user's
compilation.

## Does `dump=pretty` parse with the plugin's Haxe parser?

Measured by feeding real haxe 4.3.7 `dump=pretty` output through
`HaxeParserDefinition` (ParsingTestCase, counting `PsiErrorElement`s):

- **Raw `Main.dump`** (unrolled loops, inlined `map`, object literals,
  `_g ++` temporaries, `};` block terminators, `@:value`/`@:keep` metadata):
  5 error elements, **all** caused by the `` `trace `` backtick-marked
  unbound identifier (one real error plus cascade).
- **Packaged std dump**: 2 error elements, both from the dotted declaration
  name (`class haxe.iterators.ArrayIterator<T>` — dots are illegal in a
  declared class name). The non-standard property access
  `var array(default,ctor)` and dotted type-parameter references
  (`Array<haxe.iterators.ArrayIterator.T>`) parse WITHOUT errors.
- **Sanitized version** — backticks stripped, declared class name un-dotted
  (the package belongs in a `package` statement instead): **0 error
  elements**.

So no custom parser or highlighter is needed: after a two-rule textual
sanitizer (strip `` ` `` markers; split the dotted declaration name into
`package` + simple name), the dump parses as ordinary Haxe and the existing
file type provides highlighting, folding and structure view for free.

### What the backtick means (grammar-extension option)

The backtick is not printed by the dump writer — it is part of the
identifier itself. In the typed AST, `TIdent` is an **unbound identifier**
(one bound to no declaration; Haxe's own docs call it "an unknown
identifier"). The typer manufactures exactly one backticked name,
``TIdent "`trace"`` (typer.ml: the js/python fast-trace path under DCE),
using the backtick prefix because no source identifier can contain one —
guaranteed collision-free, and each generator special-cases it. So in a dump
a leading backtick reads as "compiler-internal unbound identifier".

Instead of sanitizing, the Haxe grammar could accept it: lex `` `name `` as
one token and add an expression rule for it — `unboundIdentifier` is the
name matching the compiler's own semantics. That removes the only body-level
parse failure at the source, keeps the preview text byte-identical to the
compiler's output, and is harmless for normal source (where the construct
simply never lexes today).

### Read-only view must not run annotators

Requirement: the preview file gets navigation (resolve is on-demand and
unaffected) and lexer-based syntax highlighting, but no daemon passes — no
annotators, no inspections, no compiler-diagnostics wiring. The platform
mechanism is `ProblemHighlightFilter` (EP
`com.intellij.problemHighlightFilter`, `intellij.platform.analysis.jar`,
public API — verified: no `@ApiStatus` restrictions in 2026.2): return
false from `shouldHighlight()` for the preview's virtual file (recognized by
a user-data key on the `LightVirtualFile`) and the daemon skips the file
entirely while the editor keeps syntax colors, folding and go-to-declaration.

## Verdict

Viable and cheap for a signature-level preview — the blueprint carries far
more than the current render uses, and the virtual-file mechanism plus
navigation already work. Bodies are impossible over the display protocol by
design; `-D dump=pretty` is the documented opt-in alternative if that need
ever materializes.
