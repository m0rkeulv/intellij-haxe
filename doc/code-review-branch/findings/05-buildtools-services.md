# 05-buildtools-services

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/buildtools/HaxeDefineContextService.java:15 (also HaxeLibrarySync.java:18, HaxeLimeProjectInfoService.java:21, HaxeNmeProjectInfoService.java:16)
Package direction violation, verbatim checklist item: "model/buildtools code never imports UI/toolwindow classes — a constant or store being the excuse means it lives in the wrong package." Four buildtools services import `v2.toolwindow` types: `HaxeActiveBuildFileStore`, `HaxeEnvironmentStore`, `HaxeTargetSelectionStore`, `HaxeBuildSettingsListener` and the tree model types `HaxeBuildFile`, `HaxeBuildFileScanner`, `HaxeBuildFileType` (from `v2.toolwindow.tree`). These are stores and domain model, not UI — they belong in `v2/buildsystem` or `v2/buildtools`, with the toolwindow depending on them, not the reverse. The fix is moving those classes out of the toolwindow package (a mechanical move; registrations in plugin.xml lines 466-470 update with them).

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/buildtools/HaxeNmeProjectInfoService.java:84
The whole background-evaluation machinery is a copy of `HaxeLimeProjectInfoService` — `CacheKey`, `cache`/`inFlight`/`pendingCallbacks` fields, the bounded single-thread executor, `getCachedOrSchedule`'s freshness/attempt logic, `invalidate`, and `schedule`'s drain-callbacks-before-dropping-in-flight dance (the subtle ordering comment is copied verbatim at Lime:158 and Nme:166). The javadoc admits it ("Mirrors {@link HaxeLimeProjectInfoService}"). This is nontrivial concurrency code: a bug fix in one must be remembered in the other. Extract the scheduling/caching skeleton into one shared helper (generic in the evaluation type, taking the run function and an optional on-evict hook for the prepared dir); each service keeps only its tool-specific run/parse code.

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/buildtools/settings/ui/HaxeBuildToolsSettingsPanel.java:40
`sdkCombo.setRenderer(new SimpleListCellRenderer<>() { ... })` is exactly the workaround CLAUDE.md's deprecation example calls out: the deprecated `SimpleListCellRenderer.create` factories say "Doesn't support rounded selection. ### question — src/main/java/com/intellij/plugins/haxe/v2/buildtools/HaxeDefineContextService.java:147
`boolean changed = before != null && !Objects.equals(before, after);` — the `before != null` guard (added, per the comment, to stop null-vs-null from swallowing changes... actually to compare against `lastComputed`) also swallows the null→non-null transition. Scenario: files are parsed while no v2 active build file is configured (`getActiveDefines()` returns early without setting `lastComputed`), then the user activates a build file; `buildSettingsChanged()` fires, `before` is null, `after` is the new define map — `changed` is false and no reparse happens, leaving stubs built against the legacy context. If the activation path reparses through some other channel this is fine; otherwise the condition should be `!Objects.equals(before, after)` (null-vs-null is already equal, so the original swallow the comment describes does not need the extra guard).

### minor — src/main/java/com/intellij/plugins/haxe/v2/buildtools/settings/HaxeFrameworkTargetSettings.java:138
`defaults()` spells the identical mapping lambda `target -> new TargetDefinition(target.toString(), target.getOutputTarget(), List.of(target.getFlags()))` three times (once per enum), and `defaultTargetName()` (line 128) is a second per-framework switch over the same trio. The three enums (`LimeTarget`, `OpenFLTarget`, `NMETarget`, all in `common/.../config`) expose the same shape; giving them a small shared interface (`getOutputTarget()`, `getFlags()`, plus a `DEFAULT` accessor) collapses both switches to one mapping — the "per-type switch that must grow" checklist item, applied at the domain's home in `config`.

### minor — src/main/java/com/intellij/plugins/haxe/v2/buildtools/settings/ui/HaxeBuildToolsConfigurable.java:95
`apply()` stops every compilation server unconditionally, even when the apply only changed an unrelated field (neko/hashlink/haxelib path) — throwing away every warm server cache, which is the server's whole value. Gate the `stop()` on the server-relevant fields (enabled/port/arguments) or the SDK actually having changed.

### minor — src/main/java/com/intellij/plugins/haxe/v2/buildtools/HaxeDefineContextService.java:51
The constructor subscribes `this` as a message-bus handler before `this.project` is assigned. A `buildSettingsChanged()` published from another thread in that window reaches `refreshAsync()` with `project` still null and NPEs. Assign `this.project = project` first; subscribing a not-fully-constructed `this` last at least narrows the leak to the ordinary listener-in-constructor pattern.
