# 03-toolwindow-stores

### fix-now — src/main/java/com/intellij/plugins/haxe/v2/toolwindow/HaxeActiveBuildFileStore.java:59,69 (also HaxeEnvironmentStore.java:90,131,146,160,177,201; HaxeTargetSelectionStore.java:60,73)
Every mutator publishes BEFORE it mutates: `setActiveFile` runs `notifyChanged();` and only then `state.activeFile = filePath;` (same pattern in every setter and in all three `loadState` overrides, where the notification even precedes `this.state = state`). The topic is a `syncPublisher`, so listeners execute while the store still holds the old value: `HaxeDefineContextService.buildSettingsChanged()` nulls its snapshot and schedules `refreshAsync()` immediately — the background recompute can read the pre-change state on a pooled thread and is never re-triggered after the assignment lands, leaving a stale define context; the tool window's synchronous `refreshTree` subscriber rebuilds from old state too. Swap the order in every mutator: mutate first, publish last.

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/toolwindow/HaxeEnvironmentStore.java:118,191
`clearContainer` and `putDefine` mutate without calling `notifyChanged()`, unlike every sibling setter in the same class (`setDefines`, `removeDefine`, `setSdkName`…). The callers compensate exactly the way the topic's own javadoc says they shouldn't ("new invalidation sources publish the same topic instead of every consumer learning about every source"): `HaxeAddDefineAction.java:36` calls `panel.refreshTree()` after `putDefine`, which repaints the tree but leaves `HaxeDefineContextService` uninvalidated — a user define changes conditional compilation yet no reparse fires. `clearContainer` (called from `HaxeModuleWorkspace.kt:71` on module removal) has the same gap. Add `notifyChanged()` to both (after the mutation, per the fix-now above) and drop the manual panel refresh.

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/toolwindow/ (package placement of all five stores + HaxeBuildSettingsListener + HaxeTargetOptions)
The checklist's package-direction rule — "model/buildtools code never imports UI/toolwindow classes; a constant or store being the excuse means it lives in the wrong package" — is violated wholesale by this package. `HaxeEnvironmentStore` is imported by ten-plus non-UI files (`v2/buildtools/HaxeDefineContextService`, `HaxeCompileCommands`, `HaxeLibrarySync`, `HaxeToolPathResolver`, `HaxeProjectTaskRunner`, `v2/display/HaxeCompilerDisplayService`, `HaxeDisplayConfiguration`, `util/HaxeModuleDetection`, `codeInsight/daemon/HaxeProjectSdkSetupValidator`…); `HaxeActiveBuildFileStore`, `HaxeTargetSelectionStore`, `HaxeTargetOptions`, `HaxeCustomActionsStore`, `HaxeBuildFilesStore` and `HaxeBuildSettingsListener` are likewise pulled into `v2/buildtools` (LimeProjects, NmeProjects, HaxeBuildFilesProjectAware, HaxeDefineContextService). These classes are project configuration and target metadata, not UI — nothing in them touches Swing. Move them (and the listener topic) to a non-UI package, e.g. `v2/buildtools/settings` or a new `v2/config`, so the import direction holds.

### minor — src/main/java/com/intellij/plugins/haxe/v2/toolwindow/HaxeCustomActionsStore.java:29-30
The store mixes vocabularies: the state class is `ContainerActions` but its key field is `ownerId`, while the sibling stores' identically-shaped classes (`ContainerFiles`, `ContainerEnvironment`) key on `containerId` — and the class javadoc says the key is actually the build file's path, not a container id at all. Pick one name that states what the key is (e.g. `buildFilePath`, with the class renamed accordingly), instead of a container-named class keyed by an owner-named field holding a file path.

### minor — src/main/java/com/intellij/plugins/haxe/v2/toolwindow/HaxeBuildFilesStore.java:94-110 (with HaxeCustomActionsStore.java:119-136, HaxeEnvironmentStore.java:220-237; and HaxeCustomActionsStore.java:61-73 with HaxeEnvironmentStore.java:103-115)
The `find`/`getOrCreate` pair — stream the state list, match on the id field, append a new entry when absent — is spelled three times, once per store, and the type-erasure sanitize loop ("stored lists can carry foreign objects after a format change") twice (`sanitizeActions`, `sanitizeDefines`). Per the duplication rule, the same expression spelled in 2+ places gets one named home: a small shared helper (list + id-extractor + factory) would collapse all three lookup pairs, and one `retainInstancesOf(list, Class)` both sanitizers.

### minor — src/main/java/com/intellij/plugins/haxe/v2/toolwindow/HaxeTargetOptions.java:35,60
`TargetChoice` carries `id` and `displayName`, but both construction sites build it as `new TargetChoice(target.name(), target.name())` — the two components are identical by construction, and the class javadoc concedes it ("Ids are the configured names"). A record field that can never differ from its sibling is dead weight for every consumer that must pick one; either collapse the record to a single value or give `displayName` a real source. If the split is reserved for the planned profiles work, a TODO naming that must say so.

### minor — src/main/java/com/intellij/plugins/haxe/v2/toolwindow/HaxeCommandRunner.java:63-64
The `createNotification(...)` argument list wraps across two lines. Per the wrapping-call rule, the long computed argument gets a name first: extract `String title = HaxeBundle.message("haxe.command.runner.failed", presentableName);` (and optionally the notNullized message) so the call collapses to one line stating the intent.
