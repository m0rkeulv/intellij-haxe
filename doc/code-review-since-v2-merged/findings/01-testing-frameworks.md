# 01-testing-frameworks

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/testing/HaxeTestGutterContext.java:46
The per-file cache depends on `PsiModificationTracker.MODIFICATION_COUNT`, which bumps on *every* PSI change anywhere in the project, so `compute` reruns on essentially every keystroke — and `compute` walks `candidateTestsPaths`, which enumerates every hxml **and every XML file** in project scope (`FileTypeIndex.getFiles`, twice) and then, per surviving candidate, calls `HaxeBuildClasspaths.sourceDirectories` and `HaxeTestFrameworks.detectedFrameworkFor`, each of which independently re-resolves the file and re-runs `HaxeBuildSections.inspectSelected` (uncached — it re-parses the hxml sections / lime xml every call). That is a full-project index scan plus two parses per candidate on the gutter-marker path. Fix: depend on a structural tracker (VFS/`store.getModificationTracker()` plus a build-file-content tracker) rather than `MODIFICATION_COUNT`, hoist `candidateTestsPaths` to a project-level cached value, and inspect each candidate build once — pass the already-computed `HaxeBuildFileType`/`HaxeBuildFileInfo` into the framework lookup instead of calling `detectedFrameworkFor(project, testsPath)`, which redoes `findFileByPath` + `detectType` + `inspectSelected`.

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/testing/HaxeTestFramework.java:22
The interface is missing the one thing every framework has that callers still switch on: its shipped reporter root. `HaxeTestLaunchPlanner.reporterClasspath` (line 112) is a `switch (framework.libraryName())` with a `case` per implementation returning `HaxeTestReporterFiles.<name>Classpath()` — the exact "per-type switch that must grow with every new type wants to be an interface method the types implement themselves" case from the checklist. Every other per-framework fact (`supportsInterp`, `supportsFlash`, `singleRunTemplate`, `filterArgs`) already lives on the interface; adding a fifth framework means editing the planner rather than just adding a class. Fix: add `@Nullable String reporterClasspath()` (or `Optional<String>`) to `HaxeTestFramework`, implement it in the four framework classes, and delete the switch.

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/testing/MunitFramework.java:55
`MunitFramework.reportingArgs` and `TinkFramework.reportingArgs` (TinkFramework.java:58) are character-for-character identical apart from the macro string (`intellij_munit.Macro.init()` vs `intellij_tink.Macro.init()`) and a comment word, and `BuddyFramework.reportingArgs` (BuddyFramework.java:72) repeats the same null-guard + `teamcity_suite_name` block with a different tail. The `"teamcity_suite_name="` define name itself is spelled in four separate Java files (Buddy:82, Munit:65, Tink:68, Utest:86) with no named home, so a rename has to be chased by grep. Fix: one shared package-private helper — e.g. `HaxeTestReporterArgs.withSuiteName(suiteName, reporterClasspath, String... tail)` holding the `SUITE_NAME_DEFINE` constant — with munit/tink passing `"--macro", "intellij_<lib>.Macro.init()"` and buddy passing its `reporter=` define.

### minor — src/main/java/com/intellij/plugins/haxe/v2/testing/HaxeTestFrameworks.java:33
`return detected != null ? detected : ALL.get(ALL.size() - 1);` encodes "utest is the default" as "whatever happens to be last in `ALL`", so the class javadoc's two claims (detection order, and the default) are silently coupled — reordering `ALL` for detection reasons changes the default with nothing to catch it. Fix: `private static final HaxeTestFramework DEFAULT = new UtestFramework();` (reused as the last `ALL` element) and return `DEFAULT`.

### minor — src/main/java/com/intellij/plugins/haxe/v2/testing/HaxeTestGutterContext.java:43
`contextFor`'s javadoc says "null when no **marked** tests build owns it", and `HaxeTestRunLineMarkerContributor`'s class javadoc (line 25) says a marker appears "only when a **MARKED** tests build owns the file" — but `candidateTestsPaths` (correctly documented on the class itself, line 83) also accepts *conventional* candidates (`test.hxml`/`tests.hxml`, files under `tests/`) minus the excluded ones, which is the whole point of "a project that never explicitly marked anything still gets markers". Both comments state behaviour the code no longer has. Fix: say "marked-or-conventional tests build" in both places.

### minor — src/main/java/com/intellij/plugins/haxe/v2/testing/HaxeTestFramework.java:81
The `singleRunFilterArgs` javadoc — "Extra compiler arguments a single-TEST run adds beyond its template (utest's UTEST_PATTERN)" — names only utest, but `MunitFramework` also overrides it (`-D intellij_munit_test=<method>`, MunitFramework.java:90), and the `singleRunTemplate` javadoc above it likewise describes munit's both-granularities-from-one-template arrangement as utest-only.
