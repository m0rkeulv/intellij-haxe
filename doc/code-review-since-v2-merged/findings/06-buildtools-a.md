# 06-buildtools-a

### fix-now — src/main/java/com/intellij/plugins/haxe/v2/buildtools/HaxeDefineContextService.java:100
`getActiveDefines()` now opens with `HaxeKnownBuildFiles.effectiveActivePath(project)` in place of the plain store read `HaxeActiveBuildFileStore.getInstance(project).getActiveFilePath()`. That call sits ABOVE the `fastState` short-circuit whose own javadoc (lines 66-72) states the contract: *"Lock-free identity of every input reachable without VFS or read-action work … this runs per candidate inside index lookups, so the fast path must not touch findFileByPath or take a read action."* When no active file is stored — the exact case this change was made for — `effectiveActivePath` falls through to `HaxeKnownBuildFiles.all()`, which iterates every module, runs `HaxeBuildFileScanner.scan(module)` (documented "Must run in a read action", walks content-root children and can run a Haxe PSI check in `detectType`) and `LocalFileSystem.findFileByPath` per stored manual path — on every call, uncached, outside any read action. The callers are hot: `HaxeDefineDetectionManager.getAllDefinitions()` feeds `HaxeConditionalExpression` (per conditional-compilation node), `HaxeFastColorAnnotator`, `LookupUtil` and `HaxeIndexUtil`. Lines 221 and 235 (`isDefinedWithoutOverrides`, `activeContainerId`) take the same call but are cold enough to tolerate it. Fix: keep the raw store read on the fast path and resolve the implicit single-file fallback once, cached and invalidated on the build-settings topic (`HaxeBuildSettingsListener`) the service already implements — or at minimum compute it inside the existing `ReadAction.computeBlocking` and behind the `fastState` check.

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/buildtools/HaxeCompileCommands.java:122
`producesSwf` is a hand-rolled per-type if-chain over `HaxeBuildFileType` that re-derives what `HaxeBuildSystem.launchTarget` — the interface this same branch added precisely so "run/debug callers stop growing per-type switches" — already answers: lime `FLASH_FAMILY_TARGETS`→`LimeProjects.targetFor` maps `flash`/`air` to `HaxeTarget.FLASH`, nme's `targetFor` does the same, and the HXML branch is literally `HaxeBuildSections.inspectSelected(...).target() == FLASH`, i.e. `HXML_SYSTEM.launchTarget`. The whole body reduces to `HaxeBuildSystem.of(type).launchTarget(project, new HaxeBuildFile(file, type)) == HaxeTarget.FLASH`. The duplication has already diverged: lime treats `air` as swf-producing, nme's branch tests only `"flash".equals(...)`, so an nme `air` build still rides `--connect` and hits the corrupt-swf case the method exists to prevent. Fix: delegate to `launchTarget` (and drop the private chain), keeping the swf explanation as the method's javadoc.

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/buildtools/HaxeBuildFileActions.java:26
The added `defaultBuildActionName(HaxeBuildFileType)` is a second copy of `HaxeToolWindowModelBuilder.defaultBuildActionName` (line 425), which the branch left in place — the same per-type dispatch spelled in two files, which the checklist wants in one named home. Worse, the two copies disagree on HXML: the new one returns `HxmlProjects.BUILD_ACTION` (`"Build"`), the toolwindow one returns `HaxeBundle.message("haxe.toolwindow.action.build")`, and `addDefaultActions` names the HXML action node from that bundle key. The two agree only because `haxe.toolwindow.action.build=Build` in the English bundle; the moment that key is translated or reworded, `findAction(actions, defaultBuildActionName(HXML))` in the toolwindow and the run-configuration action names produced via `HaxeProgramLaunches`/`HaxeTestRunConfiguration` stop resolving to the same action. Fix: delete the private copy, have the toolwindow call `HaxeBuildFileActions.defaultBuildActionName`, and give the HXML action node the non-localized `HxmlProjects.BUILD_ACTION` identity (localize only the label, if a label is wanted).

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/buildtools/HaxeCompilationServerManager.java:204
The trust guard added to `restartServer` sits AFTER `stopInstanceLocked(instance)` and `clearServerDerivedState(id)`, and its early `return` skips `fireStateChanged()` — which only `startLocked` (line 274) fires on this path. An untrusted restart therefore kills the process and leaves every console/toolwindow listener showing the old running state and port, unlike `stopServer` (line 172), which fires after a successful stop. Fix: move the `HaxeProjectTrust.checkForBackgroundEvaluation(project)` check above `stopInstanceLocked` (nothing has been torn down yet, so returning is clean), or fire `fireStateChanged()` before the early return.

### minor — src/main/java/com/intellij/plugins/haxe/v2/buildtools/HaxeBuildClasspaths.java:18
The class javadoc claims the `-cp` entries are "the resolved `-cp` entries of its selected section (lime/nme resolve through their effective hxml)". They do not: `HaxeBuildSections.inspectSelected` routes non-hxml types to `HaxeBuildFileInspector.inspect`, which for OPENFL/LIME/NMML returns `ProjectXmlParser.parse(content)` — the raw `<source path>`/`<classpath name>` entries of project.xml — and `HaxeLimeProjectInfoService` (`lime display`) is never consulted here, unlike `HaxeDefineContextService.effectiveInfo`. HXP_PROJECT falls to `HaxeBuildFileInfo.EMPTY` and contributes nothing. Fix: state what the code does (raw `<source>` entries for the lime family) or route lime through the cached display info the way the define context does.
