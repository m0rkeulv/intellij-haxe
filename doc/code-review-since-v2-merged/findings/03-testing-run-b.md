# 03-testing-run-b

### fix-now — src/main/java/com/intellij/plugins/haxe/v2/testing/run/HaxeTestRunConfigurations.java:65
`findOrCreate` unconditionally does `configuration.setFilterPattern(filterPattern)` on a configuration it may have just *found*, and the whole-build match key is only the build file path (class/method both empty). Both production callers (`HaxeToolWindowPanel.java:286` and `:290`) pass `null`, which `setFilterPattern` notNullizes to `""` — so pressing Run/Debug on a tests row in the tool window silently erases the "Test filter pattern" the user typed into that very configuration's editor, and the run then executes the whole suite. Fix: apply the pattern only when the caller supplies one (`if (filterPattern != null) configuration.setFilterPattern(filterPattern);`), or drop the parameter entirely — see the next finding, no caller ever passes a non-null value.

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/testing/run/HaxeTestRunConfigurations.java:33-39
The public 3-argument `findOrCreate(project, buildFilePath, filterPattern)` has zero callers anywhere in `src/main` or `src/test` — the only call at line 109 is `launch` reaching the private 5-argument overload. It is also a pure pass-through that only binds two nulls. Per the dead-code checklist ("consumer-less API is deleted or carries a TODO naming the wiring it waits for"), delete it; with it gone the `filterPattern` parameter on `run`/`debug`/`launch`/`findOrCreate` is likewise never non-null and should go too.

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/testing/run/HaxeTestReporterFiles.java:32-58
`utestClasspath` / `munitClasspath` / `buddyClasspath` / `tinkClasspath` are four bodies that differ only in three per-framework constants, and they are selected by a string switch on the library name in `HaxeTestLaunchPlanner.java:113-116` (`case "utest" -> …`). That is exactly the per-type switch that "must grow with every new type" the checklist says wants to be an interface method: `HaxeTestFramework` already carries `libraryName()`, `reportingArgs()` and `singleRunTemplate()`, so the reporter's resource root, directory name and source-file list belong there as a default-returning method (e.g. `reporterSources()`), leaving `HaxeTestReporterFiles` with just the generic `extract`. As written, adding a fifth framework requires edits in two unrelated files with no compiler help.

### should-fix — src/main/java/com/intellij/plugins/haxe/v2/testing/run/HaxeTestRunConfiguration.java:161-170
The `ReadAction.computeBlocking` argument is a three-step block lambda that also builds the `LimeDisplayInputs` payload inline across five wrapped argument lines, two of them computed calls (`resolveHaxelibExecutable(...)`, `selectedTargetFlag(...)`). This breaks both "give a non-trivial lambda a name" and "a call whose argument list wraps gets its longest pieces named first — and when it still wraps, the payload itself". Extract a private `LimeDisplayInputs limeDisplayInputs(VirtualFile file, HaxeBuildFileType type)` whose body names the computed pieces and assigns `LimeDisplayInputs inputs = new LimeDisplayInputs(...)`, so the call site collapses to `ReadAction.computeBlocking(() -> limeDisplayInputs(file, type))`.

### minor — src/main/java/com/intellij/plugins/haxe/v2/testing/run/HaxeTestRunConfiguration.java:167

### minor — src/main/java/com/intellij/plugins/haxe/v2/testing/run/HaxeTestReporterFiles.java:66-77
Every reporter source is read out of the jar twice — once in the digest loop (`digest.update(readResource(resourceRoot, file))`) and again in the write loop (`Files.write(target, readResource(resourceRoot, file))`). Read each file once into a local `Map<String, byte[]>` (or a `List` parallel to `sourceFiles`), digest from it, then write from it; the same expression computed twice becomes one named value.

### minor — src/main/java/com/intellij/plugins/haxe/v2/testing/run/HaxeTestRunConfiguration.java:245

### minor — src/main/java/com/intellij/plugins/haxe/v2/testing/run/HaxeTestRunConfigurations.java:130-138

### minor — src/main/java/com/intellij/plugins/haxe/v2/testing/run/HaxeTestRunConfigurationEditor.java:73-91

### minor — src/main/java/com/intellij/plugins/haxe/v2/testing/run/HaxeTestLocator.java:25
`PROTOCOL = "haxe:test"` is the named home for the protocol string, but `HaxeTestFramework.resolveTestLocation` re-spells it as a bare literal (`if (!"haxe:test".equals(protocol)) return null;` at `HaxeTestFramework.java:102`) — the same constant in two places. ### minor — src/main/java/com/intellij/plugins/haxe/v2/testing/run/HaxeTestOutputAttributor.java:62
The span cache is keyed on the raw regex group — `spansByPath.computeIfAbsent(matcher.group(1), this::methodSpans)` — while `resolveFile` normalizes with `FileUtil.toSystemIndependentName` only *after* the lookup. Two spellings of one file (`src\unit\X.hx` vs `src/unit/X.hx`) therefore occupy separate entries and re-run the PSI resolve. Normalize once in `testNameFor` and key the map on the normalized path, passing that to `resolveFile`.

### question — src/main/java/com/intellij/plugins/haxe/v2/testing/run/HaxeTestRunConfigurationEditor.java:58
